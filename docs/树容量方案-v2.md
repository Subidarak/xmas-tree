# 树容量方案 v2（只出方案，未实施）

> 目标：让树上能挂超过 12 张照片。
> 状态：**仅设计文档，代码零改动**。当时仍为 12 张。
> 日期：2026-11-17

---

## 一、12 张是怎么回事

照片不是随便摆的，它们站在一个**固定半径的圆柱面**上：

```js
// 几何（computeGeom）
gHt    = Math.min(H * .66, W * .92, 620);   // 树高
gBaseR = gHt * .30;                          // 底半径
// 照片环绕（frame 内）
var ring = baseR * 1.05;                     // 环绕半径，固定值
var tx = Math.cos(ang2) * ring;
var tz = Math.sin(ang2) * ring;
var ty = cy + Ht * .5 - o.hf * Ht;          // 高度由 hf 决定
```

排布公式（reflow）：

```js
o.angT = 0.55 + i * (TAU / Math.max(1, n));        // 角度均分整圈
o.hfT  = n === 1 ? .46 : (.32 + .38 * (i / (n - 1)));  // 高度 32%~70%
```

**算一下周长占用（卡片宽 66px）：**

| 设备 | 树高 gHt | 环绕半径 ring | 周长 | 12 张占 | 24 张占 |
|---|---|---|---|---|---|
| 桌面 1280×800 | 528 | 166 | 1045px | 76% | **152%** |
| 手机 390×844 | 359 | 113 | 710px | **111%** | 221% |

结论：
- 桌面 12 张还剩 24% 空隙，是舒服的
- **手机 12 张已经压线**，再挤会糊成一团
- 24 张在任何设备上都要重叠一倍

外加高度带只有 `.32 ~ .70`（约 38% 树高），12 张竖直间距才 18px，本来就靠角度错开和透视分层，不是靠高度。

**所以"加数量"不能只改一个数字，必须改排布逻辑本身。**

## 二、五个方案

### A. 溢出队列（树上 12，库房更多）

**改法**
- 后端 `MAX_TOTAL: 12 → 24`
- 前端 `addCloud` / 轮询里只保留**最新 12 张**上树，老的留在数据里不渲染

```js
// cloudJoin 里，loadCloud 前过滤
var shown = Object.keys(known).length;
if (shown >= MAX_PHOTO) return;   // 不渲染，但数据还在
```

**代价**：第 13 张之后的朋友，自己挂的看不见了（除非清空重来）。
**观感**：完全不变。
**改动量**：前后端各 5 行。

---

### B. 双半径双层（树上真能站 24）

**改法**：环绕半径按圈变化，两层错开。

```js
function reflow() {
  var n = photos.length;
  var perRing = 12;
  var rings = Math.ceil(n / perRing);
  for (var i = 0; i < n; i++) {
    var o = photos[i];
    var r = Math.floor(i / perRing);        // 第几圈
    var idx = i % perRing;

    // 角度：圈内 12 等分，外圈错开半格
    o.angT = 0.55 + idx * (TAU / perRing) + r * (TAU / perRing / 2);

    // 高度：两圈各占一段，避免同高互撞
    o.hfT = (r === 0)
      ? (.34 + .16 * (idx / (perRing - 1)))   // 内圈：下半段
      : (.56 + .16 * (idx / (perRing - 1)));  // 外圈：上半段
  }
}
```

半径也要分：

```js
// frame 里，原 var ring = baseR * 1.05;
var ring = baseR * (1.05 + 0.07 * (Math.floor(idx / 12)));
```

**效果估算**：每层 12 张，各自占 76% / 82% 周长，不重叠。
**代价**：
- 外圈更靠前，透视下卡片会明显大一圈，两层观感不统一
- 高度带被切成两段，每段只有 16% 树高，层内竖直更挤（需要在缩卡片上配合）
- **必须真机看**，纸上算不出好看不好看

**改动量**：`reflow` + 半径一行 + 后端数字，约 20 行。

---

### C. 缩小卡片 + 拉高分布

**改法**
- `CARD_W/H: 66×82 → 54×68`
- `hfT` 范围 `.32~.70 → .24~.78`

**效果**：24 张至少需要周长 24×54 = 1296px，桌面 1045px 仍不够，**必须配合方案 B 的双层**才成立。
**代价**：照片明显变小，手机上更难看清脸——这是最伤观感的。
**改动量**：2 个常量 + 高度公式。

---

### D. 环上分页自动轮换

**改法**：树上始终 12 张，每 8 秒整批淡出换下一批。

```js
// 新增一个轮换状态
var pageIdx = 0, pageT = 0;
// 每批 12 张，pageT 到 8s 时 pageIdx++，全批 pp 归零再进场
```

**代价**：照片会自己动、会消失，容易让人以为没挂上；看完一整棵需要等。
**观感**：变了，而且是"活"的变化，风险高。
**改动量**：约 60 行，还要处理与拖拽旋转的冲突。

---

### E. 树上 12 + 底部横滑画廊

**改法**：环上只放最新 12，其余进底部可滑动的缩略条，点开看大图。

**代价**：手机上底部横滑与"拖动旋转树"的手势容易打架，要写手势仲裁。
**改动量**：约 120 行，最大。

## 三、对比

| 方案 | 树上能站几张 | 观感变化 | 改动量 | 风险 |
|---|---|---|---|---|
| A 溢出队列 | 12（数据 24） | 无 | 10 行 | 低 |
| B 双半径双层 | 24 | 有（层间大小差） | 20 行 | 中，需实测 |
| C 缩卡片 | 24（需配 B） | 大（照片变小） | 5 行 | 中 |
| D 轮换 | 12（总量不限） | 大（会动） | 60 行 | 高 |
| E 画廊 | 12 + 无限 | 中 | 120 行 | 高 |

## 四、建议

**先上 A**：后端放宽到 24、树上仍显示 12，改动 10 行，观感零变化。好处是数据不丢、朋友不会看到"挂满"，坏处是第 13 张之后自己也看不见。

**真想让树上站 24，就做 B**，但要准备两轮真机验收：

1. 桌面 1440 宽挂满 24 张，截图看层间有没有互相遮
2. 手机 390 宽挂满 24 张，截图看卡片是否小到看不清脸
3. 两轮都过再上；任一轮不过就回退到 A

**不建议 C 和 D**：C 伤"照片能看清"这个基本功能，D 会让照片自己动，跟"安静挂着的树"这个调性冲突。

## 五、实施时要注意
